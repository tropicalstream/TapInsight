X3 Pro × Android APIs,
Health Connect & On-Device AI

The X3 Pro is Android — so AI and Google APIs run natively on the glasses, no bridge. Here's the realistic on-device AI stack, Health Connect for body metrics, and the Android/Google APIs worth wiring into AR — with the two constraints that decide what actually runs.

00What's native, and two honest constraints

Unlike the Apple bridge, most of this runs directly on the glasses — the Android SDK, Play services, Health Connect, ML Kit, Maps/Places/Routes, CameraX, and the cloud Gemini API are all in-process. TapInsight proves it: Google Calendar, Tasks, Places, Routes, News, Contacts tools + a cloud-Gemini voice pipeline all ship on the glasses today.

⚠️ Constraint 1 — the chip likely can't run AICore / Gemini Nano

On-device Gemini Nano (via Android's AICore + ML Kit GenAI) is gated to flagship silicon — Pixel 8–9, Galaxy S24+, "progressive on Snapdragon 8 Gen 3." The X3's AR1 Gen1 is a compact AR chip; assume AICore is absent. On-device LLM here means a bundled Gemma via MediaPipe / LiteRT, or the cloud Gemini API. Probe for AICore; never depend on it.

⚠️ Constraint 2 — the glasses have no heart/SpO₂ sensor

IMU, cameras, mics — no PPG, no ECG, no pulse oximeter. Health Connect on the glasses is empty unless a Wear OS watch or wearable fills it. Compute is native; the sensors still need a wrist.

Apple guide: Watch ──▶ iPhone (must bridge: HealthKit/AI) ──▶ glasses Android (this): Watch ──▶ Health Connect ──▶ glasses read it natively AI + Google APIs run ON the glasses (no bridge) …but live vitals still need the wrist sensor

01What 2025–2026 changed

Gemini Nano 4 (2026) and Gemini Intelligence (announced at The Android Show, May 12 2026) — Google's most advanced on-device Android AI, served through AICore, but device-gated (Constraint 1). ML Kit GenAI Prompt API is the entry point when AICore is present — summarize/rewrite/describe-image, no key, no cloud. Gemma 4 via AICore preview, and Gemma runnable locally via MediaPipe / LiteRT — the device-agnostic path that works on the AR1. Health Connect is now the health hub (Google Fit sunsets end of 2026).

02On-device & cloud AI — the realistic stack

Four tiers, "definitely runs on the AR1" → "only if the chip cooperates":

tier 1Cloud Gemini API — multimodal, no device gate, already wired in TapInsight. Takes the glasses' camera frame + text. The heavy-reasoning path.

val parts = listOf(
  Part.text("HR $hr bpm. What is the camera looking at, anything notable?"),
  Part.inlineData("image/jpeg", cameraFrameBase64))
geminiClient.generateContent("gemini-2.5-flash", parts)

tier 2MediaPipe LLM Inference / LiteRT — bundle a quantized Gemma and run it in-process. No AICore. The offline path. But it's a sustained load on a 4-core/4 GB/thermally-tight device — gate it, keep generations short, never run it under the dim mask (the reboot lesson).

val opts = LlmInference.LlmInferenceOptions.builder()
  .setModelPath(".../gemma3-2b-it-int4.task").setMaxTokens(512).build()
LlmInference.createFromOptions(context, opts).generateResponse("Summarize: $text")

tier 3ML Kit — on-device OCR, translation (50+ langs), barcode, face/pose, smart reply. Cheap, reliable, offline — the AR HUD primitives (translate a sign in view, read text aloud, scan a QR).

tier 4AICore / Gemini Nano — probe at runtime; expect absent on the AR1, fall through to tiers 1–2. Write the capability check, not the assumption.

Live workout data comes from Health Services on a Wear OS watch (MeasureClient/ExerciseClient) — the watch forwards to phone/glasses. Same JSON envelope as the Apple guide, so the glasses-side consumer is identical regardless of ecosystem: {"type":"health","hr":78,"spo2":98,"steps":8421}.

Notably NOT on the X3

ARCore — vendor docs confirm none; 6-DoF is SLAM/ShareCamera only (why the object-tracking POC uses MultiSet REST). Google Fit APIs — sunset end of 2026, use Health Connect. Wear-only live measurement — needs the watch.

The standout direct wins (REST + key, nothing but OkHttp): Maps/Places/Routes/Air-Quality/Directions — the glasses already call these; a new one is a tool class, not an architecture.

05–06Glasses side, and honest limits

The glasses half is light — starter-guide patterns: receive the envelope, render a metrics tier (white-on-black, throttled redraws), feed changes to the readout engine, ring the bell on thresholds.

Limits, honestly: the AR1 is thermally tight (4 cores, 4 GB, >500 mA = trouble) — an on-device LLM is a sustained load; gate it and obey the masked-redraw rule or reproduce the reboot. No on-glasses heart sensor — live vitals need a wearable. No medical claims — consumer SpO₂/HR are wellness signals. APIs move fast — fetch the live Android docs and confirm every signature before building.
